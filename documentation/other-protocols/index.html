    BACP and other protocols¶

    BACP does not start from scratch. Several open protocols for agentic commerce and agent communication already exist, and BACP reuses their ideas and wire formats wherever they fit. This page explains how BACP relates to each one, and what it takes from each.

    The descriptions are based on each protocol's public specification or announcements as of 17-10-2026. These protocols change quickly, so check their own documentation for the current state.

    Complementary, not competing

    BACP is an India-specific agent layer. It reuses the ideas and, where they fit, the wire formats of the global protocols, so that an agent built for them can work in India with less extra effort, and so that BACP can track their evolution. Where BACP's wire format differs, this page says so.

    UCP¶

    The Universal Commerce Protocol is an open standard for interoperable commerce between platforms (such as AI agents), businesses and payment providers. Businesses publish a profile at a well-known URL. Platforms negotiate capabilities such as checkout, cart, catalogue and orders, and the same operations are bound to REST, MCP, A2A and an embedded binding. UCP versions its specification by date.

    How BACP relates. BACP's checkout session follows UCP checkout's lifecycle and status names (BACP spells cancelled and adds human_handoff). BACP is not wire-compatible with UCP. Paths, totals and the sign of discounts, the ucp envelope, the complete payload and payment authority, and the MCP argument shape differ. A gateway that lists the capability in.bacp.ucp_checkout also serves a projection in the shape of the UCP checkout, pinned to UCP release v2026-08-25, and UCP clients use that projection. BACP adds what UCP leaves out for India: discovery across a network rather than per business, write paths after an order (cancel, return, grievance), Indian payment rails, DPDP consent and GST.

    Where BACP differs from UCP. The table lists every difference that matters to an agent built for UCP, in the order in which such an agent fails. The first row is the one that moves money: a UCP-built agent that reads a BACP discount as a UCP discount shows the buyer an extra charge instead of a saving. UCP facts are as of 18-10-2026, from UCP's release v2026-08-25 (25-08-2026), the latest of its four releases, which is also the release the projection pins (Q-82). Text that UCP added to its main branch after that tag is not in the pinned release and is not described here as UCP's behaviour.

    How the two are organised. UCP is organised as services (verticals such as shopping), capabilities inside each service, a common layer shared by all, and extensions that add to a capability. BACP has the same four ideas under different names, and they do not line up one to one. BACP's counterpart of a UCP vertical is a trade profile: a set of rules for one kind of buying (for example B2B trade or public procurement) over the same capabilities. What UCP calls "Common" is spread over BACP's shared artefacts, which every capability uses.

    Among the UCP parts with no BACP counterpart in this version are the cart capability, linking a buyer's account at a seller, ask (natural-language questions to a business, which is on UCP's main branch after v2026-08-25 and in no release as of 18-10-2026), permalink (a browser-addressable intent), location search and lookup, and a second vertical, lodging. These are parked, not rejected, each with the controls it needs written into an open question: the cart (Q-95), linking a buyer's account at a seller (Q-96), ask (Q-97), loyalty (Q-98), catalogue lookup by id and variants (Q-99) and purchasable ranking parameters (Q-100). The UCP projection answers 404 for them. A third party can define a new capability only through capability_declarations and the digest-pinned registry, which activates once a registry review exists (Q-94); how a new vertical is added stays an open topic.

    What BACP does not take from UCP. BACP does not adopt UCP's Embedded Protocol, in which a business's own checkout page runs inside the platform's surface and can collect payment and address details. This is a non-goal, not a gap. In BACP the principal's authorisation happens on the Trusted Surface, the non-agentic surface of the Mandate Manager or the payer's PSP, which renders only gateway-signed content in the principal's language and takes the PIN or biometric itself. A seller's page does not take part: it is not non-agentic by requirement, it cannot be checked against a signed render, and putting a PIN or a consent on a seller's page would put the factor within reach of the party that benefits from the answer. A merchant-supplied view for a human to review a basket before approving stays parked; if it is added, the approval would still be given on the Trusted Surface.

    What BACP reuses from UCP.

    • Checkout session lifecycle and status names, and recovery when a response is lost.
    • The pattern of defining operations once and binding them to REST, MCP and A2A.
    • HTTP Message Signatures (RFC 9421) with Content-Digest (RFC 9530), with ES256 and EdDSA (Ed25519) both mandatory to verify.
    • Idempotency-Key semantics and date-based versioning.
    • Capability intersection between the two parties' profiles, and payment handlers as a concept.
    • The approach to publishing the specification: MkDocs with an unversioned landing site and versioned specification paths.

    AP2¶

    The Agent Payments Protocol (AP2) is a security layer for agent payments that sits inside a commerce protocol. As of 17-10-2026, version 0.2 (released in April 2026) defines checkout and payment mandates, each open (constraints) or closed (exact cart or payment), as SD-JWT credentials with key binding. A non-agentic Trusted Surface collects the user's consent, and each verifier returns a signed receipt. AP2 assumes that agents may be attackers and requires verification in deterministic code. On 28-04-2026 the FIDO Alliance announced that Google had donated AP2 to it, and work on the specification continues in FIDO working groups (as of 17-10-2026).

    How BACP relates. BACP's mandate model is AP2 v0.2's model, with Indian semantics added. BACP adds periodic budgets (AP2's budget is cumulative over the mandate's life), category and PIN code allow-lists, step-up thresholds, cancel, return and grievance scopes, revocation with a short propagation target, and a PSP-attested binding to a live UPI primitive. Negotiation bounds are carried in a separate negotiation mandate, so that AP2 verifiers, which fail closed on unknown constraints, still accept BACP's Checkout and Payment Mandates.

    What BACP reuses from AP2.

    • Open and closed Checkout and Payment Mandates, encoded as SD-JWT with key binding to the agent's key.
    • The non-agentic Trusted Surface for consent and authentication.
    • Fail-closed evaluation of constraints, and treating the agent as untrusted.
    • Signed receipts from each verifier, as the basis of dispute evidence.

    ACP¶

    The Agentic Commerce Protocol (ACP) defines a merchant-hosted REST API for checkout sessions, in which the merchant remains the system of record, and a delegated payment API that issues a vault token limited by an allowance. OpenAI and Stripe developed ACP and were its first implementers. ACP was described as being in beta (reported, not verified as of 17-10-2026).

    How BACP relates. ACP's allowance is single-use and tied to one checkout session, and its delegated payment is card-only. BACP needs standing mandates for when the user is not present, and Indian rails. BACP borrows ACP's response and error conventions, which are well suited to agents.

    What BACP reuses from ACP.

    • Authoritative full-state responses on every call.
    • The flat error object and messages[] with a resolution hint.
    • Strict idempotency rules: a missing key, a conflicting body, a request still in flight and a replay each have a defined response.

    A2A and MCP¶

    A2A lets agents delegate tasks to other agents. MCP connects a model host to tools and data. Neither defines commerce or payments. They are transports.

    How BACP relates. BACP is bound to both, as UCP is. A BACP gateway can be offered as MCP tools and as an A2A extension, as well as over REST.

    What BACP reuses.

    • From A2A: the agent card for discovery, the TASK_STATE_AUTH_REQUIRED task state as the point where a step-up is requested, and structured data parts for BACP objects.
    • From MCP: tool bindings with structured content, OAuth 2.1 with audience-bound tokens, and the insufficient_scope challenge as the step-up trigger.

    Read more: MCP and A2A.

    Visa Trusted Agent Protocol and Mastercard Agent Pay¶

    Card networks run their own agent programmes. Visa's Trusted Agent Protocol signs agent requests with RFC 9421, using different signature tags for browsing and for paying (agent-browser-auth and agent-payer-auth in its reference code), with created and expires timestamps and a nonce. Visa Intelligent Commerce issues agent-specific payment tokens and checks each payment against the user's authenticated instruction. In Mastercard Agent Pay only registered agents can transact, using Mastercard network tokens. Verifiable Intent, which Mastercard published as an open specification, contributed to the FIDO Alliance (announced 28-04-2026) and plans to integrate into Agent Pay (as of 17-10-2026), is a layered SD-JWT credential that carries the user's Checkout and Payment Mandates.

    How BACP relates. These programmes cover card rails. BACP covers the Indian rails around them, and can carry a network agentic token as one payment handler among many.

    What BACP reuses.

    • Separate signature tags for browsing and paying, which BACP extends with tags for post-order actions, negotiation and the Trusted Surface.
    • Nonce-bound, short-lived signatures with a replay cache.
    • A handler for network agentic tokens (in.card.agentic), marked as a pilot.

    x402¶

    x402 is an HTTP 402 flow for paying per request: the server answers with a payment challenge, the client retries with a signed payment, and a facilitator verifies and settles it. As of 17-10-2026, implementations settle in stablecoins and tokens on blockchain networks. The specification says it aims to support fiat networks too.

    How BACP relates. x402 addresses per-request payment for APIs and content, not the order lifecycle. It does not cover INR rails. BACP does not use x402 today. The 402 challenge pattern may be worth reusing for paid APIs on Indian rails in the future.
