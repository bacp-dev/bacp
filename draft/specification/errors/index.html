    Errors¶

    BACP reports problems on two channels, following the ACP error model. A request that the gateway could not accept fails with an HTTP error status and a flat Error object. A request that the gateway accepted, but whose business outcome the agent must act on, succeeds (200 or 201, or 202 where the operation is accepted asynchronously) with the full authoritative state and a messages[] array. This page defines both shapes, the resolution vocabulary that tells an agent what it may do next, and the registry of every code a conforming participant may emit.

    Version 2026-10-18

    This page is part of BACP version 2026-10-18. Rules marked Proposed depend on an open question and may change in a later dated release. Codes are stable identifiers. A participant MUST NOT emit a code that is not registered on this page.

    Two channels¶

    Channel When HTTP status Body
    Protocol failure The request was malformed, unauthenticated, unauthorised, refused by the deterministic mandate verifier, or could not reach the seller. 4xx or 5xx One flat Error object
    Business outcome The request was processed and the resource has a new authoritative state, but the agent must take note, ask the principal, or wait. 200 or 201; 202 for asynchronous operations (POST /mandates, return requests, Trusted Surface events) The full resource (session, order, negotiation, …) with messages[]

    Rules:

    1. A gateway MUST return protocol failures as 4xx or 5xx with a flat Error. It MUST NOT wrap them in a 200.
    2. A gateway MUST return business outcomes as 200, 201 or (for asynchronous operations) 202 with the full resource state and messages[]. The agent MUST treat the returned state as authoritative and MUST NOT reconstruct state from earlier responses.
    3. Step-up is never only an error. When a human must approve, the resource moves to status: requires_escalation, carries a step_up object, and carries the message step_up_required with resolution: requires_buyer_review. See Mandates and Consent and Sessions and Checkout.
    4. param is an RFC 9535 JSONPath into the request (for an Error) or into the returned resource (for a message), for example $.mandate_ref or $.payment.scheduled_debit_at. Header problems use $.headers.<Name>.

    Dual-channel codes¶

    Some validator and guard codes can appear on either channel. The rule is:

    • the code is a 200 message when it describes an incoming counterparty object or a computed outcome (a handler intersection, a seller's offer);
    • the code is a 403 error when it blocks the caller's own outgoing commitment (a firm COUNTER, an ACCEPT, a bid, an award, a session update or complete).

    For example, handlers_incompatible is a 200 message on POST /payment-handlers/intersect and a 403 error on an ACCEPT whose agreed payment option has no eligible handler. Registry rows marked "200 msg / 403" follow this rule.

    A code that also appears as a 200 error message on a session cancelled by a mandate event (mandate_expired, mandate_revoked, mandate_paused, rail_binding_not_open_eligible) mirrors that code's error status: the message reports the same condition that complete would return as an error.

    The Error object¶

    Field Type Required Meaning
    type enum yes Error class: invalid_request, authentication_error, authorization_error, mandate_error, payment_error, upstream_error, service_unavailable
    code string yes A code from the registry
    message string yes Human-readable explanation for logs and developers. Agents MUST NOT present it to the principal as a legal notice.
    param string no RFC 9535 JSONPath to the offending field
    resolution enum no How the agent should proceed; one of the resolution values. Gateways SHOULD send it.
    reasons array of string conditional Every local and rail reason that applied. REQUIRED on rail-cap and step-up errors.
    step_up_kind enum conditional confirm or rail_auth. REQUIRED on step-up errors.
    supported_versions array of string conditional The versions that the gateway lists. REQUIRED on version_unsupported and absent on every other code.
    capability string conditional The capability id that owns the refused member. REQUIRED on capability_unsupported and absent on every other code.
    reason enum conditional no_conforming_origin, language_unavailable or channel_not_allowed. REQUIRED on trusted_surface_unavailable and absent on every other code. Not to be confused with reasons.
    seller_reason object conditional On bpp_nack only: {code, beckn_code}, the reason the seller refused. code is item_unavailable, quantity_reduced, price_changed, not_serviceable, store_closed, agent_orders_not_accepted, terms_mismatch or other. The gateway sets it only from the BPP-signed NACK, and an unmapped Beckn code gives other. Which ONDC code maps to which value is for ONDC to answer.
    handoff_routes array of HandoffRoute conditional On trusted_surface_unavailable with reason language_unavailable or channel_not_allowed: the session's ai_disclosure.handoff_routes, so that the agent can offer the principal a human. Absent when the session lists none.
    step_up object conditional On 403 presence_not_proven for a post-order write without hp_proof: a StepUp of kind post_order (reason presence_proof) that the principal confirms on the Trusted Surface to obtain the proof (Presence proof).

    Rail-cap and step-up errors MUST also carry reasons[] (every local and rail reason that applied) and step_up_kind. idempotency_in_flight and quota_exceeded MUST be sent with a Retry-After header.

    {
  "type": "mandate_error",
  "code": "mandate_revoked",
  "message": "Mandate mdt_PAY7Q2W9X4K1M3 is REVOKED",
  "param": "$.mandate_ref"
}

    The Message object¶

    Field Type Required Meaning
    type enum yes error, warning, info or disclosure
    code string yes A code from the registry
    origin enum conditional Who wrote content: gateway (the default when args is absent) or counterparty. REQUIRED whenever args is present.
    content LangText yes Multilingual text keyed by BCP 47 tag, for example {"hi-IN": "…", "en-IN": "…"}. A gateway-written content never contains counterparty text.
    args array no Values inserted at {name} placeholders in content, each {name, origin, text}. A counterparty value (an item name, a fee label) travels only here, with origin: counterparty.
    param string no RFC 9535 JSONPath into the returned resource
    resolution enum yes What the agent may do next (see Resolution) 
    {
  "type": "warning",
  "code": "payment_in_doubt",
  "content": {
    "en-IN": "Debit status unknown. Reconciling with the PSP. Do not retry with a new key."
  },
  "param": "$.payment.status",
  "resolution": "recoverable"
}

    The first message of every checkout session is the ai_disclosure message (type: disclosure), which carries the agent's AI notice in the principal's language and points (param: $.ai_disclosure) at the session's typed routes to a human.

    For a message with type: disclosure and a code registered below with that type (sponsored_listing, sponsorship_undeclared and prior_price_claim), an agent that presents the session to a principal MUST present the fixed phrase for that code from Disclosure phrases, in the principal's language, next to what param names, with the item's name, as labelled seller text, taken from the session line whose item is the catalogue[] entry's item_id, never from args. It fills the phrase's slots from the Disclosures.catalogue[] entry that param names. It MUST NOT summarise, hide or drop the message, and it hands off to a human rather than present it in a reduced form. It never reads the message's content in place of the fixed phrase. A type: disclosure message with an unregistered code is treated as info: the agent records it and does not read it verbatim. ai_disclosure keeps its own rule.

    Resolution¶

    Every Error code and every message has exactly one resolution. On a seller-side gateway a code whose registry resolution is requires_buyer_review is emitted with requires_seller_review, because the principal who reviews is the seller's. The one exception is rail_binding_not_open_eligible, whose registry row gives a resolution per cause; the Error.resolution field then carries the one that applies:

    Value Meaning for the agent
    recoverable The agent may fix the request itself (re-select, wait, GET and retry with the same key) without involving the principal.
    requires_buyer_input The agent must ask the principal for something new: set up or renew a mandate, choose another payment method, supply missing data.
    requires_buyer_review A human must review and approve on the Trusted Surface (step-up, disclosure review, out-of-scope action). The agent MUST NOT approve on the principal's behalf.
    requires_seller_review The same, for the seller principal: a message that a seller-side gateway emits and that its principal reviews, in the seller application or on the seller's Trusted Surface. The agent MUST NOT approve on the seller principal's behalf. A buyer-side gateway never emits it.
    unrecoverable The request cannot succeed as sent. The agent must not retry it; an operator may need to act.

    "Informational" is not a resolution value. Purely informational messages use type: info with resolution: recoverable.

    Client behaviour¶

    • An agent that meets a code it does not know MUST act on the HTTP status class (and, for messages, on resolution). It MUST NOT retry a 4xx with a new Idempotency-Key: a new key is a new purchase intent and is evaluated against the mandate afresh.
    • After a 5xx, a timeout or a lost response, the agent MUST first GET the resource and MAY then retry only with the same Idempotency-Key (see REST binding).
    • On payment_in_doubt the agent MUST NOT re-key. The gateway reconciles with the PSP and reports the outcome.
    • A new code MUST be registered here, with its HTTP status and resolution, before any participant emits it.
    • A conformance run fails on any unregistered code (see Conformance).

    Registry¶

    "200 msg" means the code arrives in messages[] on a 200 or 201 response. "200 + step_up" means the resource moves to requires_escalation with a step_up object. A dash in the Typical param column means no single field applies.

    Transport, identity and idempotency¶

    Code HTTP type Meaning Typical param Resolution
    invalid_request 400 invalid_request Generic schema or parse failure. Also returned when an order-scoped request is ambiguous because the agent holds the same order id from two sellers and did not name the seller, and when a session's basket_id is already used by sessions of another principal, presence or root open Checkout Mandate. Also returned when BACP-Version is missing and the profile lists more than one version (at $.headers.BACP-Version), when a quantity is not a multiple of the item's increment (at $.items[n].quantity), when fulfilment.option_id names an option that the session did not offer (at $.fulfilment.option_id), and when a basket is below a min_order (at $.items). the offending field; $.bpp_id for an ambiguous order; $.basket_id recoverable
    version_unsupported 400 invalid_request The request names, in BACP-Version, a version that the gateway's profile does not list. The error carries supported_versions[]. A request that omits a header that is REQUIRED because the profile lists more than one version is not this code: it is invalid_request at $.headers.BACP-Version. $.headers.BACP-Version; supported_versions carries the listed versions recoverable (choose a listed version)
    version_mismatch 409 invalid_request A request for a session names a version other than the one the session was created under. Nothing changes. $.headers.BACP-Version recoverable (name the session's version, or create a new session)
    capability_unsupported 400 invalid_request A request carries a member that a capability owns, and the gateway's version defines that capability but the gateway does not list it (for example discounts without in.bacp.discounts, payment_plan or a session_id on POST /payment-handlers/intersect without in.bacp.payment_plan, or a UCP buyer.consent, loyalty or cart_id member on the UCP projection). Nothing is created or changed. The content of an MCP result is the fixed capability_absent sentence (Disclosure phrases). It is not the discount_code_unsupported warning, which is a listed capability whose seller declines. the member path, for example $.discounts; capability carries the capability id unrecoverable
    idempotency_key_required 400 invalid_request Idempotency-Key is missing on a POST or PUT, or is not 22–64 printable ASCII characters. $.headers.Idempotency-Key recoverable
    idempotency_conflict 422 invalid_request The same key was reused with a different request body. A retry that adds hp_proof to a refused 403 presence_not_proven write is such a case; its message names a new key. $.headers.Idempotency-Key unrecoverable (a new key only for a new intent), or recoverable when the only change is hp_proof (retry with a new key)
    idempotency_in_flight 409 + Retry-After invalid_request A request with the same key is still being processed. — recoverable (retry with the same key)
    idempotency_store_unavailable 503 service_unavailable The idempotency store is unreachable; writes fail closed. — recoverable
    request_too_large 413 invalid_request The request body exceeds the gateway's limit (at most 256 KiB). Checked on raw bytes before signature verification. — unrecoverable
    quota_exceeded 429 + Retry-After invalid_request The agent has too many live idempotency keys or too many requests in flight, or the caller exceeded a rate limit: render fetches per Mandate Manager or PSP key, counted before the lookup, and per key and step-up after the standing check, or post_order step-ups created per (agent, principal) and per order. Retry-After is REQUIRED. The figures are the gateway's own, published in its profile (Limits on step-ups). — recoverable
    signature_invalid 401 authentication_error The RFC 9421 signature does not verify, lacks a required covered component, is outside its time window, or uses a tag that the endpoint or the credential's purposes does not allow. Also a handoff accept or release signed by a key whose registry role is not support_operator. $.headers.Signature-Input unrecoverable
    replay_detected 401 authentication_error The (keyid, nonce) pair was already seen within the signature window. $.headers.Signature-Input unrecoverable
    agent_unregistered 401 authentication_error The signing key or the AgentCredential does not resolve in the registry. — unrecoverable
    agent_credential_revoked 401 authentication_error The AgentCredential is revoked on its status list. — unrecoverable
    trusted_surface_only 403 authorization_error The caller is an agent, not a registered Mandate Manager or payer PSP, so it may not post Trusted Surface events or fetch a step-up's ts_render. A Mandate Manager or PSP that is not the step-up's (Step-up signers) gets 404 not_found instead. Also returned for a MandateRequest that an agent or a gateway submits with supersedes: only the principal, on the Trusted Surface, ports a mandate (Porting a mandate). — unrecoverable
    trusted_surface_unavailable 503 service_unavailable No Trusted Surface can take the step-up, and the gateway sent nothing that carries it to the principal. reason is no_conforming_origin (the signer has no registered origin the gateway may use and no ts_notify_url), language_unavailable (no Trusted Surface of the signer renders the step-up's language) or channel_not_allowed (the only channels that the mandate's confirmation floor allows are unavailable). With the last two the error carries handoff_routes[]. It is never recoverable: a bare 503 reads as "retry", and a retry cannot succeed until the signer registers an origin or a notify endpoint, or the principal chooses a route (Origins and delivery). — requires_buyer_input
    ts_render_mismatch 403 authorization_error A Trusted Surface approval's presentation.content_hash is not the sha-256 of the step-up's gateway-signed ts_render; or, for a negotiation step-up, presentation.offer_hash, the ts_render's offer_hash and the offer the step-up names differ, or the ts_render's acceptance_revocation differs from the signed offer's value. The event is refused and the session does not change. Returned to the Mandate Manager or PSP that posted it. $.presentation.content_hash, $.presentation.offer_hash unrecoverable
    not_found 404 invalid_request The resource does not exist or is not visible to the caller, including a step-up or session that belongs to another Mandate Manager's or PSP's mandate, and a handoff accept or release signed by a support_operator key of another agent operator than the session's. the path parameter unrecoverable
    session_state_conflict 409 invalid_request The operation is not allowed in the resource's current state, including an agent PUT or complete on a session in human_handoff, and a handoff accept after the handoff ended (handoff.ended_at set). Also, at $.handoff.accepted_by: a handoff accept while accepted_by is set, a release by a key of the same agent operator that is not accepted_by, and an agent release after acceptance. Also a new step-up inside the decline cool-off that follows an explicit step_up.declined, and a replacement past the seller re-prompt cap of an issue, both with no new step-up (Limits on step-ups); the cool-off answer carries Retry-After set to the time left. $.status, $.handoff.accepted_by recoverable (GET, then act on the current state)
    bpp_timeout 504 upstream_error No on_* callback arrived within the gateway's wait window. The resource remains retrievable. — recoverable (GET, then retry with the same key)
    bpp_nack 502 upstream_error The seller app NACKed the Beckn request. seller_reason carries the seller's own stated reason, when its BPP-signed NACK has one. recoverable covers only a retry of the same item at a total no higher than the one the principal was shown. A substitute item or seller at a higher total needs the principal's confirmation (Seller refusals and substitution). — recoverable

    Mandate and verification¶

    Code HTTP type Meaning Typical param Resolution
    mandate_required 403 mandate_error No mandate is referenced, or the referenced mandate is not yet ACTIVE (PENDING or REJECTED). $.mandate_ref requires_buyer_input
    mandate_invalid_signature 403 mandate_error A Mandate Manager, principal or agent signature over a mandate (or the closing key-binding JWT) does not verify, for example because the mandate was edited. $.mandates, $.kb_jwt unrecoverable
    mandate_invalid 403 mandate_error The mandate is malformed in a way the verifier cannot evaluate; the verifier fails closed. $.mandates unrecoverable
    mandate_schema_invalid 400 invalid_request The mandate fails its schema, for example an open payment mandate without rail_binding. $.mandates unrecoverable
    rail_binding_not_open_eligible 400 (also a 200 error message on a checkout session cancelled by a binding pause) invalid_request The open payment mandate's rail_binding (or the rail of a mandate request) resolves to a handler that cannot back standing authority: a reserved or deprecated descriptor, a pilot that the gateway's conformance attestation does not list in an unexpired pilots[], a handler that is not open-eligible, or a rail_binding.primitive that is not in the descriptor's binding.open_primitives. Also returned for an open payment mandate issued without rail_binding.primitive or rail_binding.registry_version, for an HNP complete when the gateway's descriptor copy is more than 24 hours old, for an HNP complete on a pilot handler when the mandate's rail_binding.conformance is absent, names another gateway, or names an attestation that is revoked or expired (binding_ineligible) or whose status list is more than 24 hours old or unreachable (attestation_status_stale), at issuance for a conformance attestation that the Mandate Manager does not accept (Conformance attestation), and at issuance for a Reserve Pay block whose payee is the buyer app, whose seller's BPP-signed payment terms the gateway does not hold and does not obtain first, or whose payee VPA is not the VPA in those terms. Evaluated against the current registry at issuance and at every complete. On complete the error carries reasons[] with the cause: binding_ineligible, reissue_required, registry_copy_stale or attestation_status_stale; at issuance it may carry attester_not_accepted (the signer is in the Mandate Manager's published exclusion list) or attester_not_independent (the authority or a funder is the same operator as the gateway, the payer PSP or the Mandate Manager, or an operator is unknown). When several reasons apply, reasons[] is ordered reissue_required, binding_ineligible, registry_copy_stale, attestation_status_stale, and resolution is that of the first. An agent that can disprove reissue_required or binding_ineligible from the mandate it holds treats the claim as a gateway fault and opens no re-issue (Handler binding). The 400 status is deliberate (see the note below this table). $.mandates, $.rail requires_buyer_input at POST /mandates, for reissue_required (have the mandate re-issued on an eligible binding) and for binding_ineligible (offer another payment method; the agent opens no resume or re-issue request without a new principal instruction); recoverable for registry_copy_stale and attestation_status_stale (a gateway or attestation-status condition: retry later, the principal is not asked)
    constraint_unknown 403 mandate_error The mandate carries a constraint key the verifier does not know. Unknown constraints fail closed. $.proposed_constraints unrecoverable
    mandate_expired 403 (also a 200 error message on a checkout session cancelled by the expiry) mandate_error The mandate is past valid_until or its rail authority has expired. A post-order write with presence: HP is not refused for this status (Post-order gate); without HP it gets 403 presence_not_allowed. $.mandate_ref requires_buyer_input
    mandate_revoked 403 (also a 200 message: error on a checkout session cancelled by the revocation, warning on negotiation sessions) mandate_error The mandate was revoked by the principal, by a rail safety switch or by agent relinquishment. A post-order write with presence: HP is not refused for this status (Post-order gate); without HP it gets 403 presence_not_allowed. $.mandate_ref requires_buyer_input
    mandate_paused 403 (also a 200 error message on a checkout session cancelled by the pause) mandate_error The principal paused the mandate, or the gateway paused it for a debit on its Reserve Pay block that matches no BACP payment (unmatched_rail_debit, removed only by the principal), and only these reasons are in force. While a gateway pause reason (binding_ineligible, reissue_required) is also in force, rail_binding_not_open_eligible is returned instead. A post-order write with presence: HP is not refused for this status (Post-order gate); without HP it gets 403 presence_not_allowed. $.mandate_ref requires_buyer_input
    mandate_exhausted 403 mandate_error A budget, the rail block or max_executions is used up, counting in-flight reservations and every Reserve Pay block at its full amount. A post-order write with presence: HP is not refused for this status (Post-order gate); without HP it gets 403 presence_not_allowed. At mandate request (and on the activation event of a sibling block) also: a requested Reserve Pay block that, at its full amount, does not fit the remaining headroom of every budget window of its root. $.mandate_ref, $.checkout_mandate_ref requires_buyer_input
    mandate_scope_mismatch 403 mandate_error The request falls outside the mandate: amount, category, merchant, PIN code, line items, checkout_hash, data shared outside data_scopes, reuse of a closed payment mandate, purpose bounds at mandate request, or a handler that does not resolve. At mandate request also: a Reserve Pay request without payee or without rail_limits.block_amount, a checkout_mandate_ref that names no ACTIVE root open Checkout Mandate of the principal, block amounts under one root (the requested one included) that would exceed its smallest budget max, or a new root open Checkout Mandate for a principal who already holds an ACTIVE root at the same Mandate Manager whose notice does not state every other root's budgets and the combined total. At complete also: a human-not-present debit to a seller with an unresolved reversal under the root (reasons: [seller_reversal_unresolved]; a human-present payment is allowed), an open mandate presented at a gateway that is not its BAP (agent.bap_id; for a mandate without one, a credential whose hash is not agent.credential_hash), and a second debit for a checkout_hash that already has a reservation or settled debit under the root. $.checkout_hash, $.mandate_ref, $.payee, $.rail_limits.block_amount, $.checkout_mandate_ref, $.agent.bap_id, $.agent.credential_hash requires_buyer_review
    amount_not_positive 403 mandate_error A payable amount, a tender or a ledger posting is zero, negative or not an integer number of paise. $.amount unrecoverable
    presence_not_allowed 403 mandate_error The request's presence (HP or HNP) is not in the mandate's presence_allowed, or a trade act (POST /trade-acts) carries presence: HNP. $.presence requires_buyer_review
    presence_not_proven 403 mandate_error A post-order write with presence: HP has no valid hp_proof: none (the error then carries step_up, a post_order step-up whose ts_render names the write, the same pending one on a repeat), one for another action, order or issue, one for RESOLUTION_ACCEPTED or RESOLUTION_REJECTED on an issue whose resolution has changed since it was shown (subject_hash), or one already used, or, for a trade act, a proof whose step-up shows a different subject than the one submitted (subject_hash: the exact document body, the ledger entry's entry_hash or the statement's head_hash; the proof is not consumed). Or, on an assisted session, a Trusted Surface approval was not made with the principal's own factor or names no assisted operator of the session. Or an ACCEPT_REVOKE of an acceptance that the principal approved on the Trusted Surface carries no valid hp_proof. Or a Trusted Surface approval of a rail_auth step-up, or of a confirm step-up whose approval releases a debit, carries user_action: voice_confirm_plus_device (Voice confirmation). Or an approval is below the mandate's confirmation_floor, or on a channel outside it (Confirmation floor), or its device_signature does not verify against the mandate's principal.device_jkt[]. Nothing is sent to the network. $.hp_proof, $.presentation.user_action requires_buyer_review
    rail_limit_exceeded 403 + reasons[], step_up_kind: rail_auth mandate_error A rail cap other than an AFA threshold would be exceeded: per-transaction, period, first-24-hour, remaining block or channel cap. $.amount requires_buyer_review
    log_chain_invalid 403 mandate_error The InstructionLog chain is broken or its head does not match the log_head sent on the network. $.log_head unrecoverable
    constraint_unresolved 200 + step_up — A constraint cannot be evaluated deterministically for this request, so the gateway falls back to a human confirmation. $.step_up requires_buyer_review
    collector_not_authorised 403 payment_error The party in collected_by is not an RBI-authorised payment aggregator or a bank according to the registry. No money moves. $.payment.collected_by unrecoverable
    receipt_invalid 400 invalid_request A receipt is malformed or is not signed by a registered PSP key. $.receipt unrecoverable
    evidence_forbidden 403 authorization_error The caller is not a party of record for the evidence bundle. — unrecoverable
    evidence_unverifiable 422 invalid_request The evidence bundle fails verification: signatures, the chain (including a negotiation receipt whose received_at is earlier than that of an entry before it in the chain without clock_step_observed; two receipts at one log_seq for different entries; a CounterSignature payload without log_seq, log_entry_hash or prev_entry_hash; under the sunset text for allowed_until_receipt, also a receipt of an ACCEPT or ACCEPT_REVOKE without log_entry_hash, or a CounterSignature that names a transcript position holding another message), or step 6 (a step-up entry without its signed Trusted Surface event, an approval without a Presentation or with a content_hash that does not match its ts_render, a step-up event whose ts_render is missing from ts_renders[] or whose total, payee or checkout_hash differs from the BPP-signed quote or whose price_breakup_hash differs from the disclosures hash, a ts_render whose catalogue_disclosure[] differs from the bundle's Disclosures.catalogue[] or omits a qualifying entry, a Disclosures.catalogue[] entry whose source_digest the agent's discover log entry does not list or whose signed source does not match, a negotiation step-up whose ts_render carries an offer_hash or acceptance_revocation that differs from the signed offer, or a first agent entry that is not ai_disclosure). A verifier reports the same code. — unrecoverable
    cancel_not_allowed 403 authorization_error The seller refuses the cancellation under its cancellation terms (@ondc/org/cancellable, cancellation_terms). A mandate or scope failure is mandate_scope_mismatch, and a presence failure is presence_not_allowed. $.order_id requires_buyer_review
    return_not_allowed 403 authorization_error The return is outside the return window, the item is not returnable, or the quantity exceeds what was ordered and not yet returned. $.items[n] requires_buyer_review

    Why rail_binding_not_open_eligible is 400. On complete, this code can be a refusal by the deterministic verifier of a well-formed, signed mandate (for example after a registry downgrade), which would normally be a 403 mandate_error. BACP keeps it on 400 invalid_request deliberately, so that one code keeps one status at POST /mandates and at complete and the registry entry stays unchanged. Moving the code to 403 was considered and not adopted. Both statuses are on the protocol-failure channel and carry the same resolution, so a client handles them the same way.

    Session and payment messages¶

    These are always 200 or 201 messages. prior_price_contradicted and prior_price_invalid arrive in messages[] of a discover response; the others arrive on a session.

    Code Message type Meaning Typical param Resolution

    Step-up reasons¶

    step_up.reason (with step_up.kind) is one of:

    Reason Kind When
    above_step_up_threshold confirm The amount is above the mandate's step_up.above_amount.
    new_merchant confirm First order with this seller under the mandate.
    outside_categories confirm The category is outside the mandate's step-up-free categories.
    first_order confirm First order under the mandate.
    above_afa_limit rail_auth The debit is above the rail's AFA threshold (₹15,000; ₹1 lakh for listed categories).
    afa_threshold_card_emandate rail_auth A card e-mandate debit above the AFA threshold.
    afa_crossborder_cnp rail_auth A non-recurring, cross-border, card-not-present payment whose acquirer requests AFA.
    split_tender_afa_on_total rail_auth The total across tenders is above an AFA threshold.
    credit_acceptance confirm (HP) Acceptance of a loan offer.
    negotiation_out_of_mandate confirm A negotiated term is outside the negotiation mandate.
    negotiation_between_reservation_and_max confirm The price is between the reservation price and total_max.
    accept_confirmation confirm The guard returned acceptable, the mandate's accept_confirmation is ask or absent, and the agent called accept. The ts_render carries offer_hash. Nothing seller-visible is sent before negotiation.step_up.approved.
    rfq_prescribes_waiver confirm An agent-created RFQ sets acceptance_revocation_required: waived, which waives the principal's own ICA s.5 right.
    seller_confirmation confirm A BPP-signed on_select or on_init carries the bacp tag seller_confirmation: the seller asks for the buyer's own confirmation (a first cash-on-delivery order, an amount above the seller's threshold, a new credit line, a credit limit exceeded, or another reason). At most one per checkout_hash.
    refund_received confirm The gateway holds a refund receipt of the order's collector's PSP and not of the payer PSP, and asks the principal to confirm on the Trusted Surface that the credit arrived ("I have received ₹X"). Only that approval releases the spend of a debited_not_confirmed debit (Usage ledger).
    constraint_unresolved confirm Fallback when a constraint cannot be evaluated deterministically, and the reason for discovery_price_changed on an item shown with a prior_price and for policy_text_mismatch.

    Refund states¶

    Receipt.refund_state is one of pending_cardholder_consent, reversed_to_bank_account, released_block, credit_note_issued, refunded_to_source (the default for a completed refund to source) and adjusted_against_dues. A card refund before the bill is paid MUST be adjusted_against_dues and MUST NOT pass through pending_cardholder_consent. See Rail Bindings.
