    Identity and Request Signing¶

    Version 2026-10-18

    This page is part of BACP version 2026-10-18. Rules marked Proposed depend on an open question and may change in a later dated release.

    This page defines who an agent is on the wire and how every request proves it: the AgentCredential, the operator behind it, RFC 9421 request signatures with signature tags, replay protection, Content-Digest, idempotency, signing on the Beckn network leg, and key rotation and revocation.

    The design goal is that an agent can never do more than its credential and its principal's mandates allow, even if the agent is fully compromised. The agent is untrusted; its key is scoped by purpose, its requests are bound to their exact bytes, and every check happens in the gateway before the request body is parsed.

    AgentCredential¶

    An AgentCredential identifies one agent, the legal entity that operates it, and the BAP whose gateway it uses. It is an SD-JWT verifiable credential with vct: in.bacp.agent.1. Its claims are defined by agent-credential.json.

    Claim Meaning
    vct Always in.bacp.agent.1.
    iss The issuer: the network registry or an issuer it accredits (Q-02).
    sub The agent id, for example did:web:agents.example.in:krishi-voice.
    iat, exp Issue and expiry times. exp MUST be no later than iat + 180 days.
    operator The operator's legal_name, entity_id (CIN, LLPIN, GSTIN or PAN) and grievance_officer; optionally an incident_contact and an ai_inventory_ref.
    bap The BAP subscriber_id and ukid (unique key id) the agent is bound to.
    agent The agent class (shopping, voice_shopping, assisted, sub_agent), model_family, build, and optionally channels, languages and uap_agent_id.
    cnf.jwk The agent's public key (RFC 7800). The matching private key signs the agent's requests and closes its open mandates.
    purposes The signature tags this key may use: any of bacp-browse, bacp-pay, bacp-post-order, bacp-negotiate.
    disclosure ai_notice (a multilingual AI-disclosure text), human_handoff_url and handoff_routes[] (typed routes to a human: channel, a tel: or https: uri, optional dtmf, only on a tel: route, languages, hours). When agent.channels includes voice, ivr or upi123pay, handoff_routes MUST contain a tel: route. The agent's first message in every session MUST present the notice and offer the handoff (Human participants).
    conformance The conformance levels the agent's stack has passed, with a signed attestation (see below).
    status.status_list The status-list uri and index idx used to check revocation.

    uap_agent_id is reserved for an agent id issued under a future NPCI agent registry. It MUST be null or absent until such a registry is published.

    conformance MUST carry levels[], the ids of the conformance levels passed (bacp.core.1, bacp.pay.upi.1, bacp.pay.all.1, bacp.neg.1, bacp.b2b.1, bacp.auction.1, bacp.ts.1), plus the signed attestation.

    RBI's directive on Storage of Payment System Data (RBI/2017-18/153, 06-04-2018) already requires RBI-authorised payment system providers to store payment data only in India. Where an agent operator's own model may process payment data is open (Q-15). Until it is settled:

    • The credential and the registry record MAY carry a data_residency statement (payment_data, llm_region, log_region, transfer_basis). It is OPTIONAL in this version.
    • A gateway MUST NOT treat a missing or incomplete data_residency statement as permission to send payment data outside India. The gateway's own storage and processing of payment data stays in India (Data localisation).

    Presenting the credential¶

    • An agent MUST send its AgentCredential, as a compact SD-JWT with only the disclosures the gateway needs, in the BACP-Agent request header on every request except the unsigned GET /.well-known/bacp and GET /payment-handlers calls.
    • The legacy header name BACP-Agent-Credential is removed in 2026-10-18. An agent MUST NOT send it, and a gateway MUST NOT accept it in place of BACP-Agent.
    • The credential header is a covered component of the request signature, so it cannot be swapped.

    Verifying the credential¶

    Before acting on any request, the gateway MUST check, and reject with 401 on failure:

    1. The credential's signature verifies against the issuer's key in the registry (agent_unregistered otherwise).
    2. The status list does not mark it revoked (agent_credential_revoked).
    3. It has not expired.
    4. bap.subscriber_id is the gateway's own BAP.
    5. The request signature's keyid resolves to cnf.jwk.
    6. The signature's tag is listed in purposes (signature_invalid).

    Agent operators and the registry¶

    Every agent is run by an agent operator, a legal entity that is onboarded and identified through the network registry. The operator:

    • holds the AgentCredential and answers for it through the named grievance officer;
    • keeps its own operator signing key separate from the agent's cnf key and out of the agent's reach. The operator key signs instruction-log entries and evidence bundles; the agent key signs requests and closes mandates. A verifier MUST NOT accept one in place of the other;
    • signs instruction-log entries asymmetrically. HMAC MUST NOT be used, because it cannot give non-repudiation;
    • keeps an AI inventory, red-teams the agent, reports incidents, and runs a kill switch that revokes its agents' credentials.

    The registry is the root of trust for every key BACP uses: AgentCredential issuers, BAPs, BPPs, Mandate Managers and PSPs. A gateway MUST resolve every key by its registry key id, for example bap.example.in|ukid-7|ed25519, and MUST NOT trust a key presented only in a request. See Registry lookup, which names the registry-record.json fields that BACP reads, among them the operator_id of a support_operator key (the agent operator that the key serves), the Trusted Surface origins of a Mandate Manager or PSP, and the legal operator, regulatory_status[] and data_residency of any subscriber. An AgentCredential's operator.entity_id and a registry record's operator.entity_ids[] use the same EntityId shape (type of CIN, LLPIN, GSTIN or PAN, and value).

    Conformance-authority keys¶

    A key of the registry role conformance_authority (Signature.role) signs conformance attestations and nothing else. Such a key qualifies only if it belongs to an entry of the public conformance-authority list; a key that the registry record or a profile presents without a list entry does not qualify. The role grants no right to sign a mandate, a receipt, a request or a rail attestation.

    • An attestation's exp is at most 180 days after its iat.
    • A verifier of an attestation reads its status list and refuses to rely on the attestation when the list marks it revoked, when the copy it holds is more than 24 hours old, or when the list cannot be reached; a stale or unreachable list does not pause a mandate, while a revocation, an expiry or a lapse of the entry or key (next bullet) does (Handler binding). This rule is fail-closed for issuing a mandate and for a new complete on a pilot handler; it never blocks a status check, a reversal, a refund or a post-order write.
    • An entry that is removed from the latest dated release of the list, whose validity has ended or whose status is revoked, and a key that is removed from its entry, no longer qualify: an attestation that rests on them is a lapsed attestation for every mandate bound to it (Rules).

    Request signatures¶

    Every agent request to a gateway, other than the two unsigned discovery GETs above, MUST carry an RFC 9421 HTTP Message Signature made with the private key matching the credential's cnf.jwk, in the Signature-Input and Signature headers.

    Covered components¶

    The signature MUST cover:

    Component When
    @method Always
    @authority Always
    @path Always
    @query Whenever the target URI has a query component, for example GET /orders/ORD-KIR-88231?bpp_id=bpp.kirana.example.in
    content-digest Always (see Content-Digest)
    bacp-agent Always: the AgentCredential header. Exception: a request under tag bacp-ts, bacp-handoff or bacp-mm-event is signed with a registry key, carries no BACP-Agent header and does not cover bacp-agent
    idempotency-key On every request other than GET and HEAD
    bacp-version Whenever the request carries a BACP-Version header. The header is REQUIRED when the gateway's profile lists more than one version (Version negotiation). A header that is present and not covered is refused with 401 signature_invalid
    content-type SHOULD be covered whenever the request has a body

    A signature that does not cover a required component MUST be rejected with 401 signature_invalid. A signer MAY cover additional components.

    Signature parameters¶

    The Signature-Input MUST carry these parameters:

    Parameter Rule
    created Signing time, integer seconds since the Unix epoch.
    expires Expiry time. expires − created MUST be greater than 0 and at most 300 seconds.
    nonce A fresh random value for every request (see Replay protection).
    keyid The id of the agent's cnf key.
    tag One of the signature tags.

    Example, for POST /sessions/{session_id}/complete:

    Signature-Input: sig1=("@method" "@authority" "@path" "content-digest" "content-type" "idempotency-key" "bacp-agent");created=1792501322;expires=1792501622;nonce="q8Fz1V2w";keyid="sakhi-2026-10";tag="bacp-pay"
Signature: sig1=:MEUCIQDexampleSignatureBase64Value=:

    Signature algorithms¶

    BACP signatures use exactly two algorithms: ES256 (ECDSA with P-256 and SHA-256) and EdDSA with Ed25519.

    • Every verifier of a BACP signature (RFC 9421 requests and webhooks, JWS mandates, receipts, ConsentReceipts, attestations and InstructionLog entries) MUST support both.
    • Every signer MUST use one of the two. A signature with any other algorithm MUST be rejected (401 signature_invalid on a request).
    • The conformance suite will carry test vectors for both. The signature values in the published examples are placeholders: they are well-formed and do not verify. Real vectors come from implementations of the specification and are offered back to it after release.

    This settles Q-42. The Beckn network leg keeps the network's own Ed25519 signing (see Network leg signing).

    Verification order¶

    The gateway MUST verify on the raw request bytes, before any JSON parsing, in this order. The first failure ends processing:

    1. Body size. A body larger than the gateway's limit (at most 256 KiB) gets 413 request_too_large.
    2. Signature-Input and Signature are present and well formed.
    3. Every required component is covered.
    4. tag is the tag the endpoint requires and is in the credential's purposes.
    5. The validity window holds (see Replay protection).
    6. Content-Digest matches the raw body.
    7. keyid resolves through the registry and the credential (401 agent_unregistered if unknown).
    8. The signature verifies.
    9. The (keyid, nonce) pair has not been seen (401 replay_detected).

    Failures at steps 2–6 and 8 return 401 signature_invalid. Only then does the gateway parse the body and apply idempotency.

    Signature tags¶

    A tag states what kind of action a request performs. An AgentCredential lists the tags its key may use in purposes, so an operator can, for example, issue a browse-only credential. Each endpoint accepts exactly one agent tag, or one of two for negotiation messages; any other tag MUST be rejected with 401 signature_invalid, even if the credential lists it. An agent endpoint that is not listed in the table below gets 401 signature_invalid as well: there is no default tag (REST).

    Tag Meaning Endpoints
    bacp-browse Reads, discovery, cart building and other non-committing calls POST /discover; POST /sessions, GET and PUT /sessions/{id}, POST /sessions/{id}/cancel, POST /sessions/{id}/handoff (action: request, and action: release before acceptance); POST /mandates, GET /mandates/{id}, POST /mandates/{id}/relinquish; GET /orders/{id}, GET /orders/{id}/returns/{rid}; GET /issues/{id}; GET /evidence/{transaction_id}; GET /evidence/{transaction_id}/summary; GET /step-ups/{step_up_id}; POST /negotiations, GET /negotiations/{id}, GET /negotiations/{id}/offers, and non-firm messages other than withdraw and accept_revoke on POST /negotiations/{id}/offers; POST /rfqs, GET /rfqs/{id}; GET /auctions/{id}; POST /payment-handlers/intersect; GET /discover/{transaction_id}/sources/{source_digest}; GET /ledgers/{id}, GET /ledgers/{id}/entries; GET /orders/{id}/documents; POST /checkout-sessions, GET and PUT /checkout-sessions/{id}, POST /checkout-sessions/{id}/cancel
    bacp-pay Commits money POST /sessions/{id}/complete; POST /checkout-sessions/{id}/complete
    bacp-post-order Mandate-scoped writes on an existing order, trade acts and ledger postings POST /orders/{id}/cancel; POST /orders/{id}/returns; POST /issues; POST /issues/{id}/actions; POST /trade-acts; POST /ledgers/{id}/entries
    bacp-negotiate Binds the principal in a negotiation Firm offers and counter-offers, withdraw and accept_revoke on POST /negotiations/{id}/offers; POST /negotiations/{id}/accept; POST /rfqs/{id}/award; POST /auctions; bids on POST /auctions/{id}/bids; POST /auctions/{id}/award
    bacp-ts Trusted Surface events and render fetches. Never an agent tag. POST /trusted-surface/events and GET /trusted-surface/step-ups/{step_up_id}, signed with the registry key of the step-up's Mandate Manager or payer PSP
    bacp-handoff A human support operator accepts or releases a handoff. Never an agent tag. POST /sessions/{id}/handoff (action: accept or release), signed with a registry key whose role is support operator
    bacp-mm-event A gateway reports a mandate event (use, relinquished, pause_changed) to the Mandate Manager. Never an agent tag. The webhook mandate.event, delivered to the mandate's audit_uri and signed with the registry key of the gateway's BAP (Mandate events)

    POST /trusted-surface/events and GET /trusted-surface/step-ups/{step_up_id} MUST accept only signatures under tag bacp-ts by the registry key of the step-up's Mandate Manager or payer PSP. For a session step-up these are the issuer of the session's mandate and the PSP named in rail_binding.psp_id of the leg's planned open Payment Mandate under the session's root; for a summary step-up over a multi-seller basket (one whose ts_render carries covers[]), only the issuer of the shared root, and no payer PSP; for a post_order step-up, the issuer of the mandate the order was placed under and the PSP named in auth_binding.psp_id of the order's closed Payment Mandate (any of them under split tender) (Step-up signers). A request under bacp-ts carries no BACP-Agent header, and its signature does not cover bacp-agent. A request that carries an AgentCredential, or is signed by an agent key, MUST be refused with 403 trusted_surface_only, whatever its tag. A request signed by any other Mandate Manager or PSP key MUST be answered 404 not_found, never 403, so that the endpoints do not reveal which sessions and step-ups exist.

    A handoff acceptance (action: accept on POST /sessions/{id}/handoff) MUST be signed under tag bacp-handoff by a registry key whose role is support operator: a key the registry issues to one human support operator of the agent operator, never to an agent and never as a shared desk key. bacp-handoff is not a value of an AgentCredential's purposes. An acceptance under any other tag, or signed by a key whose role is not support operator, is refused with 401 signature_invalid; one signed by a support operator key of another agent operator is answered 404 not_found; and one that arrives while accepted_by is set is answered 409 session_state_conflict. The same split applies to a release. Revocation of the key takes effect at the next registry refresh, as for other keys. The gateway records the key id as handoff.accepted_by (Human handoff). Only that key, under bacp-handoff, may later release the handoff (action: release). A request under bacp-handoff carries no BACP-Agent header, and its signature does not cover bacp-agent.

    The gateway signs its webhooks to the agent with a key published in its profile's keys, so that the agent can verify them. It signs the content-free app_push that it sends to a Mandate Manager's or payer PSP's ts_notify_url the same way, and a receiver that cannot verify the signature ignores the push (Origins and delivery). It signs the response of POST /discover with the same key, under RFC 9421, covering @status and content-digest (Response signature).

    Proposed

    A dedicated tag for gateway-signed webhooks, bacp-webhook, is proposed (Q-58). Until it is settled, an agent MUST verify every webhook against a key in the gateway profile's keys, MUST NOT act on a webhook that fails verification, and MUST NOT reject a webhook only because its signature has no tag or an unknown one.

    Replay protection¶

    Rule Requirement
    Window expires − created MUST be in (0, 300] seconds.
    Clock skew A receiver MUST allow, and MUST NOT allow more than, 5 seconds of clock skew: reject when now + 5 < created or now − 5 > expires.
    Nonce cache The receiver MUST keep every (keyid, nonce) pair it has accepted until that signature's expires, and MUST reject a repeat with 401 replay_detected.
    Record after verify A nonce MUST be recorded only after the signature verifies, so that forged requests cannot fill the cache.
    Bounded cache The cache is bounded by the 300-second window; entries MAY be evicted once expired.
    Shared state A gateway that runs as several instances MUST share the nonce cache in an atomic store.

    The same 5-second skew applies to every inbound signed message, including negotiation messages and the counterparty's receipts for messages BACP sent. For negotiation it is a freshness bound only: the order of two negotiation messages comes from transcript positions, never from these times (Signed seller acceptance and clock skew).

    Content-Digest¶

    Every signed request MUST carry a Content-Digest header as defined by RFC 9530, computed with sha-256 over the exact bytes of the request body, for example:

    Content-Digest: sha-256=:X48E9qOokqqrvdts8nOJRJN3OWDUoyWxBf7kbu9DBPE=:

    A request without a body carries the digest of the empty body. The receiver MUST recompute the digest over the raw bytes it received and MUST reject a mismatch with 401 signature_invalid. Because content-digest is a covered component, changing one byte of the body invalidates the signature.

    Idempotency¶

    Every POST and PUT MUST carry an Idempotency-Key. GET requests do not.

    The key¶

    • The key MUST be 22–64 printable ASCII characters and SHOULD carry at least 122 random bits (for example a UUIDv4).
    • For POST /discover the key MUST be generated afresh for each search from at least 122 random bits (for example a UUIDv4), MUST NOT be predictable from earlier keys, and MUST NOT be reused, even after the gateway's idempotency record has expired. The key binds the sellers' on_search callbacks to this search (Verifying discovery results).
    • Keys are scoped to (agent, canonical operation, path parameters). The same key on a different operation, or on the same operation with other path parameters, is a different key. The BACP-Version of a request is part of its fingerprint, which the gateway compares with the stored request's, and not part of the key's scope: the same key with the same body and another version is not a different key but a conflict (422 idempotency_conflict), and the gateway executes nothing a second time.
    • The gateway carries the key end to end: in context.bacp.idempotency_key and in the derivation of the Beckn message_id (see Network leg signing).
    • One key is one intent. A new key means a new intent and goes through mandate evaluation afresh. A closed payment mandate can still pay only once, so a new key never causes a second debit for the same checkout.

    Outcomes¶

    Situation Status Code or header
    Key missing or malformed on a POST or PUT 400 idempotency_key_required
    First request with this key As the operation defines The response is stored
    Same key, same body, after the first response The stored status Stored body, plus Idempotent-Replayed: true
    Same key, different body, or the same body under another BACP-Version 422 idempotency_conflict (unrecoverable: use a new key only for a new intent)
    Same key while the first request is still being processed 409 idempotency_in_flight, with Retry-After
    Per-agent limit of live keys or in-flight requests exceeded 429 quota_exceeded, with Retry-After
    The idempotency store is unavailable 503 idempotency_store_unavailable (writes fail closed)
    Body larger than the gateway's limit 413 request_too_large

    Rules:

    1. Body equality is semantic. Bodies are compared in JCS form, so member order and whitespace do not matter, but null and an absent member differ.
    2. What is stored. 2xx and 4xx responses are stored and replayed. 5xx responses MUST NOT be stored: a retry after a 5xx executes again.
    3. Retention. Keys MUST be kept for at least 24 hours; 48 hours is RECOMMENDED.
    4. Quotas. The store MUST bound, per agent, the number of live keys (default 10,000) and in-flight requests (default 64). It MUST NOT evict a live key early to make room.
    5. Lost responses. If an agent does not receive a response, it MUST first read the resource (for example GET /sessions/{id}) and then retry, if still needed, with the same key. It MUST NOT retry a complete with a new key to recover a lost response.
    6. Unregistered codes. A client that receives a 4xx with a code it does not know MUST NOT retry with a new key.

    Artefact signatures¶

    A BACP artefact that carries a Signature object (kid, alg, value) is signed over a payload that this section fixes, in the form that this section fixes. The two statements below are the interoperable rule: two independent implementations that follow them verify each other's artefacts.

    Form: a detached JWS. Signature.value is a detached JWS in the sense of RFC 7515 Appendix F, in its compact serialisation with the payload segment omitted: BASE64URL(protected header) || ".." || BASE64URL(signature). The b64 header parameter (RFC 7797) is not used, so the signing input is BASE64URL(protected header) || "." || BASE64URL(payload) with the payload below.

    • Protected header. {alg, kid}, and also typ where the specification requires one for the artefact. alg is ES256 or EdDSA and equals Signature.alg. The header kid MUST equal Signature.kid. A value whose header alg or kid differs from the Signature object that carries it does not verify.
    • No embedded payload. A signer omits the payload segment. A verifier recomputes the payload as below, never trusts a payload that the value carries, and refuses a value whose payload segment is not empty.
    • Which artefacts. This form applies to a Signature object. An artefact that is defined as a compact JWS that carries its payload keeps that form: the attached JWS that closes a mandate (whose payload still holds the mandate's own signatures[]), the operator's wrapper of a mandate in an evidence bundle, a CounterSignature, a ts_render (whose header carries typ: bacp-ts-render+jws, Typed JWS) and a gateway-signed notice.

    Payload: the JCS form of the artefact minus the members it excludes from its hash. The signed bytes are the RFC 8785 (JCS) form of the artefact without the members listed here, which are the members that the artefact's own hash also leaves out, so one canonical form serves both.

    Artefact Signature member Members left out of the signed bytes
    Mandate, open or closed signatures[] status, usage, signatures, and in a closed Payment Mandate record that the gateway stores, auth_binding.afa_ref (the bytes whose sha-256 is the mandate hash)
    InstructionLog entry signature signature (the entry_hash is signed)
    Receipt signature signature (the receipt_hash is over the signed receipt, signature included)
    ConsentReceipt signature signature
    Negotiation message signatures[] signatures, counter_signature, received_at (the bytes whose sha-256 is the msg_hash)
    Trusted Surface event (TrustedSurfaceEvent) signature signature
    Evidence bundle bundle_signature bundle_signature

    Where an artefact carries several signatures (a mandate has the principal's and the Mandate Manager's, a negotiation message the network participant's and the agent's), each signature covers the same payload independently. The Mandate Manager's countersignature does not cover the principal's signature, the signatures can be verified in any order, and removing one leaves the others valid. A StandingAccept and the signed objects of an auction are signed over their JCS form without signature, as their own descriptions say.

    Signature.role is outside the signed bytes, so a label proves nothing. A verifier takes a signature's role from the resolution of its kid (a registry key's role, or for principal the device key that the Mandate Manager attested), never from Signature.role. A signature whose role differs from that resolution does not count, and two entries with the same kid are invalid. A verifier that finds an artefact with two entries of the same kid counts the role that the label claims as missing and refuses the artefact with evidence_unverifiable (or mandate_invalid for a mandate).

    Network leg signing¶

    The gateway, acting as the BAP, signs its Beckn/ONDC messages with the BAP's registry key, as the network requires. On Beckn/ONDC this is an Ed25519 signature over a BLAKE2b-512 digest of the request body, sent in the Authorization header and verified against the sender's registry record. BACP does not replace this signing; the agent's RFC 9421 signature ends at the gateway.

    The network's own signing is normative on the Beckn leg. BACP does not require Beckn 2.0 signed acknowledgements; the gateway SHOULD use them, and the request-signature binding of callbacks, where the counterparty supports them. The CounterSignature that negotiation timing relies on is a BACP artefact carried in the negotiation message, not a Beckn acknowledgement (settled in Q-43; see Negotiation).

    Rules for the network leg:

    1. Deterministic message ids. The gateway MUST derive each Beckn message_id as a UUIDv5 under its published message_id_namespace over agent_id | idempotency_key | action (the exact name is in Message ids), so a retried call re-sends an identical message.
    2. Duplicate rejection. A BACP-aware receiver MUST reject a duplicate message_id within the message's ttl with a NACK. The gateway treats that NACK as "already received".
    3. Callback binding. Where the counterparty does not support signed acknowledgements, the gateway MUST bind each on_* callback to its request by (transaction_id, message_id), accept only the first, and log duplicates. An unsolicited callback with an unknown message_id is ignored and logged.
    4. Mandate binding. On init, confirm, update, cancel and IGM issue, context.bacp.mandate_ref is REQUIRED. It MAY carry a kb_jwt signed with the agent's cnf key, with aud = the bpp_id and nonce = the confirm message_id, so that a BACP-aware seller can check that the agent holds the mandate's key.

    Durable artefacts (credentials, mandates, receipts, log entries, negotiation messages) are signed separately as compact or detached JWS over their JCS form, with a key id that the registry resolves. See Mandates and Consent and Evidence and Instruction Log.

    Key rotation and revocation¶

    Key or credential Rotation Revocation
    AgentCredential and its cnf key exp at most 180 days after iat; the operator re-issues with a new cnf key The issuer marks the credential revoked in its status list. The gateway rejects it with 401 agent_credential_revoked.
    Registry keys (BAP, BPP, Mandate Manager, PSP, credential issuer) At least every 180 days Removed or marked invalid in the registry record; verifiers stop accepting signatures under it once they refresh the record
    Operator signing key Per the operator's registry record As for registry keys
    Conformance attestation exp at most 180 days after iat The authority marks the attestation revoked in its status list, or the entry is removed from the latest release of the public list (Conformance-authority keys)

    Rules:

    1. A gateway MUST re-check a credential's status no later than the end of the cached registry record's validity, and MUST NOT accept a credential after its status list shows it revoked.
    2. An operator's kill switch revokes its agents' credentials through the status list. Once a credential is revoked, the gateway sends no further network traffic for that agent.
    3. An open mandate's cnf key is part of the signed, immutable mandate. A closed mandate made with any other key fails verification. So when an agent rotates its cnf key, open mandates bound to the old key can no longer be closed, and the principal needs to approve new mandates for the new key.
    4. Mandate Manager and PSP keys sign mandates, attestations and receipts that are used later as evidence. A verifier resolves the signing key by its key id in the registry.
