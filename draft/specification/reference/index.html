    Reference¶

    Version 2026-10-18

    This page is part of BACP version 2026-10-18. Rules marked Proposed depend on an open question and may change in a later dated release.

    An index of the normative artefacts of this BACP version: the JSON Schemas, the OpenAPI document, the payment-handler registry and the example vectors. All of them are published next to this specification; the lists on this page are generated from the source/ directory of the specification repository.

    Versioned URLs

    Schema $ids have the form https://bacp.dev/schemas/<name>.json. In a published release they are served at https://bacp.dev/<version>/schemas/<name>.json, where <version> is draft, latest or a date, and every $ref inside them points to the same release. Tools MUST resolve $refs by $id, not by file path. ts-render.json refers to components of bacp.openapi.yaml; a validator loads that document as a resource under its published URL (https://bacp.dev/<version>/services/bacp.openapi.yaml).

    JSON Schemas¶

    All schemas are JSON Schema draft 2020-12.

    The human-participant types in common.json (LanguageTag, Participant, ParticipantRole, HandoffRoute, Presentation, HpProof, Actor) are described in Human Participants and the Trusted Surface.

    Schema Title Description
    agent-credential.json AgentCredential Claims of an SD-JWT VC (vct in.bacp.agent.1) issued by a registry-accredited issuer to an agent operated by a registered legal entity and bound to a BAP subscriber.
    beckn-context-bacp.json Beckn context extension: context.bacp Added to Beckn/ONDC context on every BACP-originated message. Non-BACP NPs ignore it. Mirrored in message.order.tags[descriptor.code=bacp] where a network validator rejects unknown context keys.
    common.json BACP common types Shared definitions: Amount, PositiveAmount, Hash, Jws, Jwk, Signature, Presence, LangText, LanguageTag, RailType, Channel, Handler, Duration, IssueStatus, IssueMeta, HandlerId, HandlerRef, RailTypeV1, UdyamCategory, Party, DocumentRef, Citation, ParticipantRole, Participant, HandoffRoute, Presentation, HpProof, Actor, ConformanceLevel, EntityId, QuantityUnit, ChargeRecipient, MandatePrimitiveType, OperatorCompensation, ProtocolVersion
    conformance-attestation.json Conformance attestation payload The payload of a BACP conformance attestation: a compact JWS with the JOSE header typ bacp-conformance+jwt, signed by a key in the public conformance-authority list. It records that the subject passed BACP protocol tests. It is not approval, certification or onboarding by NPCI, RBI, ONDC or any public body.
    conformance-authority-list.json Conformance-authority list The public, dated list of conformance authorities: the only way to admit a signer of conformance attestations, published as source/registry/conformance-authorities.json. It ships empty.
    consent-receipt.json ConsentReceipt (DPDP) One receipt per recipient Data Fiduciary (merchant/BPP) per mandate. Issued by the data-blind Mandate Manager acting as (or for) a DPDP Consent Manager. A receipt with consent_kind marketing (Proposed) is standalone, names one seller and carries marketing purposes and channels.
    credit-ledger-entry.json CreditLedgerEntry One entry in a bilateral, hash-chained credit ledger (khata, B2B net-N, distributor credit) behind handler bacp.credit_ledger. Both parties sign or acknowledge. No money moves on a sale entry: settlement entries reference rail receipts (RRN/UTR) of another handler.
    fx.json FX disclosure Foreign-currency view of a cross-border payment. Settlement stays INR: inr_total is an INR Amount = round(foreign_amount * rate * (1 + markup_bps/10000)).
    handler-descriptor.json HandlerDescriptor One entry of the BACP payment-handler registry. Descriptors are data: limits and rules are configuration, not code.
    instruction-log-entry.json InstructionLogEntry Append-only, hash-chained evidence of prompt -> intent -> cart -> mandate -> payment. entry_hash = sha-256(JCS(entry minus entry_hash and signature)). Raw content is stored by the operator; only hashes leave it unless an evidence bundle is requested.
    loan-offer.json Credit-at-checkout offer list (KFS) Key Fact Statement fields, unbiased multi-lender display (every matched offer, unmatched lenders named, pre-disclosed ranking metric), cooling-off, and the lender as repayment payee. RBI Digital Lending Directions 2025 paras 6(i), 6(iii), 6(iv), 8(i), 9(ii)-(iii), 10 (08-05-2025 numbering; RBI has since withdrawn these Directions in its consolidation into entity-wise directions, see Credit and Split Tender).
    mandate-negotiation.json NegotiationMandate (separate BACP negotiation mandate) A separate BACP mandate that carries the bacp.neg.* constraints, so that legacy AP2/VI verifiers, which fail closed on unknown constraint types, still accept the AP2-compatible checkout and payment mandates. Same envelope conventions as mandate.json (SD-JWT over JCS, MM + principal signatures, status list). Verified only by the buyer's guard and credential provider, never by the seller.
    mandate.json Mandate AP2 v0.2-compatible Checkout or Payment mandate, open or closed, with AA consent-artefact semantics. Everything except status, usage and signatures is signed and immutable.
    negotiation-session.json NegotiationSession Authoritative full-state view of one bilateral negotiation (one buyer, one seller, one transaction_id), as returned by the gateway (ACP full-state pattern). RFQs and auctions own several sessions.
    offer.json Negotiation messages (Offer, CounterOffer, Accept, Reject, Withdraw, Terminate, RequestExtension, AcceptRevoke, BidCommit, BidReveal, BidRetract) Structured, signed and expiring negotiation messages. Only these are binding. Discriminated by type.
    payment-plan.json PaymentPlan (split and multi-tender) How one accepted all_in_total is paid: several tenders now (gift card + UPI) and/or tranches over time (token advance + loan + balance). One closed payment mandate and one Receipt per tender. Step-up and AFA are evaluated on the plan total, never per tender.
    receipt.json Receipt (rail-anchored) Signed by the verifier that acted (AP2 Mandate/Checkout/Payment Receipt). A successful payment or refund receipt on a UPI-family handler (upi., in.upi., in.cod.upi, in.pos.tap, in.pos.dynamic_qr) MUST carry the 12-digit RRN, and carries the UTR only when the handler descriptor's settlement.evidence_refs lists utr. Any other successful payment or refund receipt MUST carry at least one of rrn, utr or rail.evidence.
    registry-record.json RegistryRecord The part of a network registry record that BACP reads about one subscriber: its id, BACP role, keys and validity, the Trusted Surface origins, notify endpoint, call numbers, languages and modalities of a Mandate Manager or PSP, the operator and person of a support operator, and, for any subscriber, its legal operator, regulatory status and data residency.
    registry-release.json RegistryRelease The manifest of one publication of the registry files: registry_version, a strictly increasing registry_serial, published_at in IST and the JCS sha-256 digest of each file. It is published as source/handlers/release.json.
    ucp/<handler id>.json UCP payment handler dev.bacp.<handler id> One schema for each of the 57 handlers of the registry (for example ucp/in.upi.circle.json): the schema of the UCP alias key dev.bacp.<handler id> that the UCP checkout projection declares. An entry carries the BACP handler id as id and no config.
    termsheet.json TermSheet Multi-issue term sheet carried in every binding Offer. Every issue carries {value, negotiable, status}. Reservation values never appear here. Issues not listed are fixed.
    ts-render.json TsRender The payload of a ts_render, the compact JWS that the gateway signs once per step-up over the JCS form of this object and serves to the step-up's Mandate Manager or payer PSP. The fields are defined on the Human participants page.

    Examples¶

    Each example is named <schema>.<case>.json and is checked against <schema>.json (rfq.* and auction.* against the Rfq and AuctionSpec definitions of negotiation-session.json, and common.<definition>-<case>.json against that definition of common.json, for example common.presentation-* against #/$defs/Presentation). A <component>.<case>.json whose <component> names no schema file is checked against the OpenAPI component schema of that name in PascalCase, for example mandate-request.* against #/components/schemas/MandateRequest and ts-render.* against TsRender in bacp.openapi.yaml. Files ending in .invalid.json are negative vectors: a conforming validator MUST reject them. The file examples/index.json is the normative map from each example to the schema or schemas it is checked against, and a validator MUST assert format (Conformance). The repository checks every vector, the index, the registry and the OpenAPI document with uv run python scripts/validate.py.
